# Modular Dashboard — Implementation Decision Log

This document captures every non-trivial implementation decision made during the route-based-navigation → single-canvas modular-grid refactor of Ghostfolio v3.0.0 — the replacement of the route-based Angular navigation shell with a single drag-and-drop dashboard canvas (built on `angular-gridster2@21.0.1`) in which every authenticated UI feature becomes an independently placeable grid module, with each user's layout persisted to the database. The document satisfies the **Explainability** project-governance rule from AAP `§ 0.8.2`, which mandates that every non-trivial decision be documented with rationale in a Markdown decision-log table — rationale lives here, not in code comments — alongside a bidirectional traceability matrix. Its intended audience is the developers, reviewers, and future maintainers of the dashboard system, and most directly the **Principal Reviewer phase of the Segmented PR Review** workflow (`CODE_REVIEW.md`), which consults this log to verify alignment between the shipped implementation and the Agent Action Plan. The structure is: a **Decision Log** with enumerated rows (`D-001` upward, with its own independent numbering), a **Bidirectional Traceability Matrix** (a forward _requirement → file_ table and a complementary reverse _file → requirement_ table), a cross-reference **References** section, and a final **Maintenance Notes** section. Because this is a refactor, the matrix explicitly maps **source navigation constructs → target module/grid implementations** at 100% coverage. Two decisions are **flagged** per the prompt's directives — `D-009` (the ChatPanel extraction) and `D-010` (the route-collapse resolution) — and are called out with a bold marker in their `Decision` cell.

## Maintenance Notes

This document is updated alongside the modular-dashboard feature it tracks. Any future material change to the implementation — a new module, a renamed or split file, a reversed decision, or a new interface — MUST be reflected here as either a new row in the Decision Log or an updated row in the Bidirectional Traceability Matrix; partial updates that leave the two tables out of sync compromise the traceability guarantee that AAP `§ 0.8.2` mandates. When a file is renamed or split into multiple files, both the forward and reverse tables MUST be updated in lockstep so that the matrix remains the canonical source of truth for "which file implements which requirement."

The **Principal Reviewer phase of the Segmented PR Review** described in AAP `§ 0.8.2` consults this document to verify alignment between the shipped implementation and the Agent Action Plan. New decisions discovered during code review are added with the next available `D-NNN` identifier and a back-reference to the Expert Agent phase that surfaced them. The decision log is intentionally append-only at the row level — a superseded decision is marked `Superseded by D-NNN` in its `Decision` cell rather than deleted, preserving the historical audit trail.
