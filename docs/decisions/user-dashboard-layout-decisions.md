# Modular Dashboard — Implementation Decision Log

This document captures every non-trivial implementation decision made during the **route-based-navigation → single-canvas modular-grid refactor** that replaces Ghostfolio's route-based Angular navigation shell with a single drag-and-drop dashboard canvas (built on `angular-gridster2@21.0.1`) whose modules each user composes and whose layout is persisted per user. It satisfies the **Explainability** project-governance rule from AAP `§ 0.8.2`, which mandates that rationale live here — in this Markdown decision-log table — rather than in code comments, and it is consulted most directly by the **Principal Reviewer phase of the Segmented PR Review** (`CODE_REVIEW.md`). The structure is: a **Decision Log**, a **Bidirectional Traceability Matrix** (a forward _requirement → file_ table and a complementary reverse _file → requirement_ table), a cross-reference **References** section, and a final **Maintenance Notes** section. Because this work is a refactor, the matrix explicitly maps **source navigation constructs → target module/grid implementations** at 100% coverage. Two decisions are **flagged** per the prompt's directives — `D-009` (the ChatPanel extraction, AAP `§ 0.1.2.2`) and `D-010` (the route-collapse resolution, AAP `§ 0.7.3`) — and every decision row cites the specific AAP section number(s) that originate or constrain it.

## Maintenance Notes

This document is updated alongside the modular-dashboard feature it tracks. Any future material change to the implementation — a new module, a renamed or split file, a reversed decision, or a new interface — MUST be reflected here as either a new row in the Decision Log or an updated row in the Bidirectional Traceability Matrix; partial updates that leave the two tables out of sync compromise the traceability guarantee that AAP `§ 0.8.2` mandates. When a file is renamed or split into multiple files, both the forward and reverse tables MUST be updated in lockstep so that the matrix remains the canonical source of truth for "which file implements which requirement."

The **Principal Reviewer phase of the Segmented PR Review** described in AAP `§ 0.8.2` consults this document to verify alignment between the shipped implementation and the Agent Action Plan. New decisions discovered during code review are added with the next available `D-NNN` identifier and a back-reference to the review phase that surfaced them. The decision log is intentionally append-only at the row level — a superseded decision is marked `Superseded by D-NNN` in its `Decision` cell rather than deleted, preserving the historical audit trail.
