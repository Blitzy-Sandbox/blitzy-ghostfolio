# Modular Dashboard Refactor — Implementation Decision Log

This document captures every non-trivial implementation decision made during the **single-canvas modular-dashboard refactor** of Ghostfolio v3.0.0 — the work that converts the application's multi-route Angular shell into one user-composable `angular-gridster2` grid at the root route `/`, on which every existing screen-level feature becomes an independently placeable module, with each user's arrangement persisted server-side to PostgreSQL. The document satisfies the **Explainability** project-level rule from AAP § 0.8.2, which mandates that every non-trivial implementation decision be documented with rationale in a Markdown decision-log table, alongside a **bidirectional traceability matrix delivered at 100 % coverage** that maps the removed routes/screens to their target grid-module implementations. Its intended audience is the developers, reviewers, and future maintainers of the modular dashboard — and most directly the **Principal Reviewer phase of the Segmented PR Review** workflow described in AAP § 0.8.2, which consults this log to verify alignment between the shipped implementation and the Agent Action Plan. The structure is: a **Decision Log** (`D-001` upward), followed by a **Bidirectional Traceability Matrix** (a forward _requirement → file_ table, a reverse _file → requirement_ table, and a dedicated _removed route/screen → disposition_ table that guarantees 100 % coverage), a cross-reference **References** section, and a final **Maintenance Notes** section. This log is a **separate, self-contained artifact** for the dashboard refactor: it uses its own `D-001`-upward identifier namespace and does **not** extend the numbering of the sibling AI-portfolio log at `docs/decisions/agent-action-plan-decisions.md`; where a decision relates to the load-bearing `var(--mat-sys-*, <fallback>)` styling discipline, it cites the originating precedent **D-020** in that sibling log rather than restating it.

The complementary **reverse** table (_file → requirements implemented_) answers "what does this file address?" and is useful when reviewing or refactoring a single file. A dedicated **removed route/screen → disposition** table guarantees **100 % coverage** of the navigation shell that the single `/` canvas supersedes. All three tables share the same underlying mapping; renaming or splitting a file MUST update them in lockstep.

## Maintenance Notes

This document is updated alongside the modular-dashboard refactor it tracks. Any future material change to the implementation — a new module, a renamed or split file, a reversed decision, or a new interface — MUST be reflected here as either a new row in the Decision Log or an updated row in the Bidirectional Traceability Matrix; partial updates that leave the tables out of sync compromise the traceability guarantee that AAP § 0.8.2 mandates. When a file is renamed or split into multiple files, the forward table, the reverse table, and (where a route/screen is involved) the removed-route disposition table MUST all be updated in lockstep so the matrix remains the canonical source of truth for "which file implements which requirement" and the removed-route coverage remains at 100 %.

The **Principal Reviewer phase of the Segmented PR Review** described in AAP § 0.8.2 consults this document to verify alignment between the shipped implementation and the Agent Action Plan. New decisions discovered during code review are added with the next available `D-NNN` identifier in this log's own namespace. The decision log is intentionally append-only at the row level — a superseded decision should be marked `Superseded by D-NNN` in its `Decision` cell rather than deleted, preserving the historical audit trail.
