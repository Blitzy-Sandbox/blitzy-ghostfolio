## Rule Rationale (relocated from production source comments)

Per the Explainability rule, the following rule/decision rationale — previously
embedded in `user-dashboard-layout.controller.ts`,
`user-dashboard-layout.service.ts`, and `dashboard-canvas.component.ts` — is
recorded here. The source files retain only concise behaviour/API documentation.

### API — `UserDashboardLayoutController` / `UserDashboardLayoutService`

- **Auth model (Rule 8).** Both layout endpoints are guarded by
  `AuthGuard('jwt')` (HTTP 401 when the JWT is missing/invalid) **and**
  `HasPermissionGuard`. Following the `getUser()` precedent in `UserController`,
  **no** `@HasPermission(...)` decorator is applied — any authenticated user may
  read/write **their own** layout (`permissions.ts` is intentionally not
  extended). `HasPermissionGuard` is a no-op when no permission metadata is
  present. The layout endpoints live in a separate controller from
  `UserController` to avoid colliding with `getUser()`.
- **Security — JWT-authoritative `userId`.** The `userId` is sourced
  **exclusively** from `request.user.id` (JWT-derived), never from the body,
  query, or params. The DTO has no `userId` field, so a client cannot
  impersonate another user. Every Prisma operation is scoped by
  `where: { userId }`. The service reads no HTTP request context, keeping it
  transport-agnostic.
- **First-visit behaviour (Rule 10).** `findByUserId` returns `null` when no row
  exists (Prisma `findUnique` does not throw); the controller maps `null` to
  HTTP 404, which the client translates to `null` to drive the blank-canvas /
  catalog-auto-open first-visit experience.
- **Idempotency / JSONB.** `userId` is the immutable primary key, so a single
  `upsert` is idempotent — re-running PATCH updates the row in place. The
  validated `layout` array is persisted into the `layoutData` JSONB column; the
  `as unknown as Prisma.InputJsonValue` cast is the documented Prisma 7 idiom for
  narrowing a typed array into a JSON column input.
- **Observability.** Per-request correlation id (honoured from an inbound
  `X-Correlation-ID` header or minted), returned as the `X-Correlation-ID`
  response header on success and the 404 path, and threaded into both service
  calls and structured logs. Metrics (`user_dashboard_layout_requests_total`,
  `user_dashboard_layout_latency_seconds`) are emitted from the service `finally`
  blocks (see D-102/D-103).

### Client — `GfDashboardCanvasComponent`

- **Single source of truth (Rule 2).** The `items` array holds module
  positions/sizes; `angular-gridster2` mutates each item's `x/y/cols/rows` in
  place, so reading `items` always reflects the latest geometry. Modules hold no
  layout state.
- **Registry is the sole introduction mechanism (Rule 3).** The canvas resolves
  every module component via `ModuleRegistryService`; it imports none of the 12
  module wrappers and inserts no component ad hoc.
- **Persistence is event-driven only (Rule 4).** `onLayoutChanged()` is the
  single funnel for all layout mutations (drag, resize, add, remove, and the
  keyboard move/resize actions). The client `DashboardLayoutService` owns the
  500 ms debounce and the PATCH; modules never call save.
- **Drag affordance.** Only the header drag-handle (`dragHandleClass`) initiates
  a drag, so interacting with the module body or its buttons never moves the
  tile.
- **Minimum footprint (Rule 6).** Each placed item carries
  `minItemCols`/`minItemRows` (≥ 2) so the engine never shrinks a module below
  the 2×2 minimum; persisted items are clamped up to the current registry minimum
  on load.
- **Material Design 3 token discipline (Rule 7 / Decision D-020).** The host
  theme uses `mat.all-component-themes()`, **not** `mat.theme()`, so the
  `--mat-sys-*` custom properties are not emitted at runtime and every
  `var(--mat-sys-*, <fallback>)` resolves to its **fallback**. The fallbacks are
  therefore load-bearing; a bare `--mat-sys-*` reference without a fallback is
  prohibited.
